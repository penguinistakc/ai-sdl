## 1. Purpose

This document defines the scope of the first release of a Pomodoro timer application. It establishes what is included, what is explicitly excluded, and the acceptance criteria against which the release will be judged. It is intended to align product, design, and engineering before implementation begins.

The product applies the Pomodoro Technique: focused work is broken into fixed-length intervals separated by short breaks, and completed intervals are tracked over time to reveal productivity patterns.

## 2. Problem Statement

People who work on computers struggle to sustain focused effort and to see, over time, whether their working habits are improving. Existing timer apps often record nothing, or record data that is never surfaced in a form that supports reflection. Users need a low-friction timer that captures each completed interval automatically and shows weekly patterns at a glance.

## 3. Goals and Objectives

| # | Goal | Success measure |
|---|------|-----------------|
| G1 | Let a user start a focused work interval with minimal friction | A user can begin a work interval in ≤ 2 actions from app launch |
| G2 | Automatically track every completed work and break interval | ≥ 95% of completed intervals are recorded without user action |
| G3 | Make weekly productivity visible | A heat map renders for the current week and any prior week with data |
| G4 | Keep the app usable offline | Core timer and tracking work with no network connection |

## 4. In Scope

### 4.1 Work Intervals (25 minutes)
- A work interval is 25 minutes by default.
- The interval counts down with a visible remaining-time display.
- The user can start, pause, resume, and cancel an interval.
- A completed work interval triggers an end-of-interval notification (audible and/or visual).
- Only intervals that run to completion count as a completed work interval. Cancelled intervals are not counted.

### 4.2 Break Intervals (5 minutes)
- A break interval is 5 minutes by default.
- A break is offered automatically when a work interval completes, and the user may accept, skip, or defer it.
- The user can start, pause, resume, and cancel a break.
- A completed break triggers an end-of-interval notification.

### 4.3 Session Tracking
- A *session* is a completed work interval together with its metadata.
- Each recorded session stores: start timestamp, end timestamp, duration, interval type (work/break), and completion status.
- Sessions persist locally across app restarts.
- The user can view a list of sessions, most recent first, for at least the current week.
- The user can delete an individual session (to correct mistakes or remove accidental runs).

### 4.4 Weekly Productivity Heat Map
- The heat map displays a grid of days (columns or rows) against time-of-day buckets or daily totals for a seven-day week.
- Cell intensity reflects the amount of completed focus time (or count of completed work intervals) in that bucket.
- A legend explains the intensity scale.
- The user can navigate to the previous and next week; weeks with no data render as empty, not as an error.
- The current week is shown by default.

### 4.5 Core Platform Behaviors
- Local persistence of settings and sessions.
- Notifications for interval completion, subject to OS permission.
- Settings for work duration, break duration, and notification sound (see 4.6).

### 4.6 Settings
- Adjustable work interval length (default 25 minutes).
- Adjustable break interval length (default 5 minutes).
- Toggle for sound and for system notifications.
- Changes to durations apply to the next interval, not the one in progress.

## 5. Out of Scope

The following are explicitly excluded from this release. They may be considered later but are not committed here.

- User accounts, authentication, and cloud sync.
- Cross-device synchronization of sessions or settings.
- Long-break intervals (e.g., a 15–30 minute break after four work intervals).
- Customizable long-break cadence and automatic cycle scheduling beyond a single work → break pairing.
- Task lists, task naming, or associating sessions with projects or tags.
- Social features, sharing, leaderboards, or team dashboards.
- Integrations with calendars, issue trackers, or time-tracking services.
- Mobile and tablet clients; this release targets a single desktop/web platform (platform TBD).
- Historical analytics beyond the weekly heat map (e.g., monthly reports, trend lines, exports).
- Reporting or data export in any format.
- Theming, localization, and accessibility certification (baseline accessibility is expected; formal audit is out of scope).
- Monetization, licensing, and onboarding flows.

## 6. Assumptions and Constraints

**Assumptions**
- The user grants notification permission; if denied, the app still functions with in-app visual alerts.
- System clock is reasonably accurate; timestamps come from the device clock.
- A week is defined as Monday–Sunday (configurable later; fixed for this release).

**Constraints**
- Single-platform release (specific platform to be confirmed during technical design).
- Timer accuracy must tolerate OS sleep/suspend: intervals are reconciled against wall-clock time on resume.
- No server component is required; the app must work fully offline.

## 7. Key User Flows

1. **Run a focus session:** launch → start work interval → 25 minutes elapse → notification → work interval recorded → break offered → break runs → break recorded → user may start another work interval.
2. **Interrupt a session:** start work interval → cancel before completion → no session recorded → timer resets.
3. **Review the week:** open heat map → current week displayed with intensity per bucket → navigate back one week → prior week rendered.
4. **Correct the record:** open session list → select a session → delete → heat map and totals update.

## 8. Functional Requirements Summary

| ID | Requirement | Priority |
|----|-------------|----------|
| FR-1 | Start, pause, resume, and cancel a 25-minute work interval | Must |
| FR-2 | Notify the user when a work interval completes | Must |
| FR-3 | Offer a 5-minute break after a completed work interval | Must |
| FR-4 | Start, pause, resume, and cancel a break interval | Must |
| FR-5 | Record each completed interval with start, end, duration, and type | Must |
| FR-6 | Persist sessions and settings locally across restarts | Must |
| FR-7 | Display a session list with delete capability | Should |
| FR-8 | Render a weekly heat map of focus activity with a legend | Must |
| FR-9 | Navigate to previous and next weeks on the heat map | Must |
| FR-10 | Allow configuration of work and break durations | Should |
| FR-11 | Allow toggling of sound and system notifications | Should |

Priorities: **Must** = required for release; **Should** = expected but negotiable under schedule pressure.

## 9. Non-Functional Requirements

- **Accuracy:** Timer drift must stay under 1 second per 25-minute interval under normal operation.
- **Reliability:** No loss of a completed session due to an app crash or restart.
- **Performance:** Heat map renders within 1 second for a week with up to 100 sessions.
- **Usability:** Primary actions reachable within two interactions from launch.
- **Privacy:** All data stored locally; no telemetry sent off-device in this release.

## 10. Acceptance Criteria

The release is accepted when:

1. A user can complete a work interval and see it recorded in the session list.
2. A user can complete a break interval and see it recorded.
3. Cancelling an interval results in no recorded session.
4. The heat map renders the current week and correctly reflects recorded sessions.
5. Week navigation works in both directions and handles empty weeks gracefully.
6. Sessions and settings survive an app restart.
7. Notifications fire on interval completion when permission is granted, and the app degrades gracefully when it is not.
8. All **Must** requirements above pass verification.

## 11. Risks and Open Questions

| # | Item | Type | Notes |
|---|------|------|-------|
| R1 | Platform decision deferred | Risk | Affects notification and persistence implementation |
| R2 | OS sleep/suspend distorts intervals | Risk | Mitigated by wall-clock reconciliation |
| R3 | Heat map granularity (hourly vs daily) undecided | Open question | Affects data model and UI |
| R4 | Notification permission denial | Risk | Mitigated by in-app visual fallback |
| Q1 | Should breaks be counted toward productivity totals? | Open question | Default assumption: no |
| Q2 | Is a session the work interval only, or work + break as a pair? | Open question | Default assumption: each interval is its own record; work intervals drive the heat map |
