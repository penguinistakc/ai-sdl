**Status:** Draft — contains unresolved decisions
**Owner:** TBD (Product)

**Requested vs. proposed:** Features (1) 25-minute work intervals, (2) 5-minute break intervals, (3) session tracking, and (4) a weekly productivity heat map were explicitly requested. All other behaviors in this document are marked `[PROPOSED]` and require product confirmation before they are treated as committed scope. ## 1. Overview and Objectives

### 1.1 Intended User

An individual knowledge worker who spends extended periods at a computer and wants to structure focused work into fixed intervals and to see, over a week, whether that structure is being sustained. The user works in a browser on a desktop or laptop and does not expect to install software. Secondary consumer of the output: the same user, reflecting on their own week.

### 1.2 Product Purpose

The product applies the Pomodoro Technique: focused work is divided into 25-minute work intervals separated by 5-minute breaks. The application times those intervals, records each completed interval, and renders a weekly heat map that summarizes focus activity so the user can see patterns at a glance.

### 1.3 Product Objectives

| # | Objective | Success measure |
|---|-----------|-----------------|
| O1 | Start a work interval with minimal friction | A user reaches a running work interval in ≤ 2 interactions from page load |
| O2 | Capture interval history without user action | ≥ 95% of intervals that reach zero remaining are recorded with no explicit save step |
| O3 | Make weekly focus visible | The heat map renders the current week and any selected prior week |
| O4 | Function in a browser with no backend dependency | All requested behavior works with the network disabled after initial page load |

### 1.4 Deployment Context

A browser-based web application with no native application dependencies. Supported browsers and any backend need have not been established (`[OPEN]` Q1, Q2). The application is assumed to run entirely client-side for this release, which is what makes O4 achievable. This assumption is load-bearing: it determines persistence, notification, and audio behavior (see §4 and §7).

## 2. Functional Requirements

Each feature below defines triggering actions or conditions and observable results. Acceptance criteria for every feature appear in §5.

### FR-1 — Work interval (25 minutes) *(requested)*

- **Trigger:** The user activates the "start work interval" control while no interval is running.
- **Behavior:** A countdown begins at 25 minutes and decreases once per second toward zero. Remaining time is displayed in mm:ss. The display is derived from a stored start timestamp and the current wall-clock time, not from an accumulating tick counter (see §4.1, §7.3).
- **Observable result:** The remaining-time display decrements; at zero remaining the interval ends and is recorded as a completed work session (§FR-5).
- **Duration source:** The 25-minute value is the default. Whether the user may change it is `[PROPOSED]` FR-9.

### FR-2 — Break interval (5 minutes) *(requested)*

- **Trigger:** Either (a) a work interval reaches zero remaining, or (b) the user activates the "start break" control while no interval is running.
- **Behavior:** A countdown begins at 5 minutes and decreases once per second toward zero. The break is visually distinguished from a work interval.
- **Observable result:** At zero remaining the break ends and is recorded as a completed break session (§FR-5). The user is then free to start another work interval.
- **Default behavior on work completion:** `[OPEN]` Q3 determines whether the break starts automatically or is offered for the user to accept.

### FR-3 — Session tracking *(requested)*

- **Trigger:** Any interval reaching zero remaining, and (for `[PROPOSED]` behaviors) explicit user cancellation.
- **Behavior:** The application creates a session record for each completed interval (see §3.1 for fields). Records persist locally and survive page reload and browser restart (§4.2).
- **Observable result:** A completed interval is retrievable from storage after reload. A `[PROPOSED]` session list view shows records most recent first.

### FR-4 — Weekly productivity heat map *(requested)*

- **Trigger:** The user opens the heat map view.
- **Behavior:** The view renders a grid of the seven days of a week. Each day cell's intensity encodes that day's completed focus total (see §3.3 for the metric and grouping rules). A legend explains the intensity scale. Controls navigate to the previous and next week.
- **Observable result:** Days with more completed focus render at higher intensity than days with less. A week with no qualifying sessions renders as an empty grid with a visible legend and zero values, not an error or a blank screen.
- **Default view:** The current week.

### FR-5 — Recording semantics *(requested, refinement of FR-3)*

- **Qualifying event:** A work interval qualifies as a completed work session when its remaining time reaches zero while the interval is running (not paused, not cancelled) and the page is executing. If the page was suspended and resumes after the interval's end time has passed, the interval qualifies as completed and is recorded on resume (§4.1).
- **Non-qualifying events:** An interval that is cancelled, or that is abandoned by closing the page before reaching zero, does not qualify and is not recorded as completed.
- **Observable result:** The count of completed work sessions equals the number of intervals that reached zero.

### FR-6 — Interval controls *(proposed)*

`[PROPOSED]` The user can pause, resume, and cancel a running interval. Pause preserves remaining time; resume continues from the preserved remaining time; cancel ends the interval without recording a completed session.

- **Unresolved:** Whether paused time counts toward the session's actual duration, and whether a paused interval that is later resumed still qualifies as completed, is `[OPEN]` Q4.

### FR-7 — Interval completion notification *(proposed)*

`[PROPOSED]` On an interval reaching zero, the application signals completion through an in-app visual change, and, where the Notification API permission has been granted, a system notification. Where sound is enabled and the browser permits audio playback, an audible tone plays.

- **Environment caveat:** System notifications and audio are subject to browser permission and autoplay policy and cannot be guaranteed (§7.2). The in-app visual change is the fallback and is always available.

### FR-8 — Session list and correction *(proposed)*

`[PROPOSED]` A list view shows recorded sessions, most recent first, for at least the current week. The user can delete an individual session. After deletion, the heat map and any totals reflect the change.

- **Unresolved:** Whether deletion is permanent or reversible is `[OPEN]` Q5.

### FR-9 — Configurable durations *(proposed)*

`[PROPOSED]` The user can change the work duration (default 25 minutes) and break duration (default 5 minutes). A change applies to the next interval started, not to an interval already running.

### FR-10 — Notification and sound toggles *(proposed)*

`[PROPOSED]` The user can enable or disable system notifications and audible completion tones independently.

## 3. Data Requirements

All data is stored client-side for this release. No server-side records exist. See §7.1 for persistence limits.

### 3.1 Session record

| Field | Type | Required | Notes |
|-------|------|----------|-------|
| `id` | string (UUID or equivalent) | yes | Stable unique identifier |
| `type` | enum: `work` \| `break` | yes | Determines whether the record contributes to the heat map |
| `startedAt` | timestamp (ISO 8601, with offset) | yes | When the interval began running |
| `endedAt` | timestamp (ISO 8601, with offset) | yes | When the interval reached zero |
| `plannedDurationSeconds` | integer | yes | 1500 for a 25-minute work interval, 300 for a 5-minute break |
| `actualDurationSeconds` | integer | yes | Elapsed running time; may exceed planned if the page was suspended (§4.1) |
| `status` | enum: `completed` \| `cancelled` | yes | Only `completed` work sessions are heat-map eligible |
| `recordedAt` | timestamp | yes | When the record was written; distinguishes suspension-recovered records |

- **Creation event:** One record per interval that reaches zero (status `completed`). One record per cancelled interval **only if** FR-6 is confirmed and `[OPEN]` Q5 resolution requires cancelled intervals to be visible in the session list; otherwise cancelled intervals produce no record.
- **Retention:** Records are retained indefinitely unless the user deletes them or the browser evicts storage (§7.1).
- **Deletion:** `[PROPOSED]` per-record deletion (FR-8).

### 3.2 Settings record

| Field | Type | Required | Default |
|-------|------|----------|---------|
| `workDurationMinutes` | integer | yes | 25 |
| `breakDurationMinutes` | integer | yes | 5 |
| `soundEnabled` | boolean | yes | `true` `[ASSUMPTION]` |
| `notificationsEnabled` | boolean | yes | `true` `[ASSUMPTION]` |
| `schemaVersion` | integer | yes | 1 |

- **Persistence:** Settings persist across reloads. A `schemaVersion` field exists so future format changes can be migrated rather than discarded.

### 3.3 Heat map — derived output

The heat map is a calculated view over session records, not a stored record set.

- **Metric:** Total minutes of **completed work** sessions per day. Break sessions do not contribute. `[OPEN]` Q6 confirms whether the metric is minutes or a count of completed work intervals; the two produce different intensities and must be fixed before implementation.
- **Grouping rule:** Sessions are grouped by **local calendar day** of `startedAt` (not `endedAt`).
- **Week definition:** Monday through Sunday. `[ASSUMPTION]` — the week start is fixed for this release and is not user-configurable.
- **Boundary conditions:**
  - A session whose `startedAt` is before midnight and `endedAt` is after midnight is attributed entirely to the `startedAt` day. `[ASSUMPTION]` — alternative is to split across days; see `[OPEN]` Q7.
  - Day boundaries and week boundaries are evaluated in the browser's local time zone.
  - Daylight-saving transitions: a local day may be 23 or 25 hours long; grouping is by calendar date, so the day is still a single bucket.
- **Empty state:** A week with no qualifying sessions renders all seven day cells at zero intensity, with the legend visible and no error state.
- **Legend:** The intensity scale (e.g., discrete bands from zero to the maximum observed value) is displayed. Whether bands are fixed thresholds or relative to the observed maximum is `[OPEN]` Q8; fixed thresholds make weeks comparable across time and are the recommended default.

## 4. Non-functional Requirements

Terms such as "fast," "responsive," and "accurate" are given measurable definitions below. Where a threshold is not yet agreed, the missing value is flagged rather than assumed.

### 4.1 Timer accuracy

- **Definition:** For an interval running in a foreground tab with no system sleep, the recorded `endedAt` must be within **±1 second** of `startedAt + plannedDurationSeconds`.
- **Requirement:** Remaining time must be computed from `startedAt` and the current wall-clock time on each render, so that accuracy does not depend on the number of timer callbacks delivered. This is required because browsers throttle or suspend timers in background tabs and on system sleep (§7.3).
- **Suspension reconciliation:** On regaining visibility or focus, the application recomputes elapsed time. If the end time has passed, the interval is finalized as completed with `actualDurationSeconds` reflecting true elapsed time, and `recordedAt` set to the recovery time.
- **Clock-change behavior:** If the system clock is set backward during an interval, the interval must not end early; behavior on clock change is `[OPEN]` Q9.

### 4.2 Persistence reliability

- **Requirement:** A session record written at interval completion must be readable after a page reload. No completed session may be lost due to a reload or a normal browser restart.
- **Caveat:** Persistence is best-effort within the browser's storage model. Storage can be cleared by the user, by private-browsing session end, or by browser eviction under storage pressure (§7.1). The application must not represent local storage as durable backup.

### 4.3 Performance

- **Definition:** "Fast" = the heat map view renders within **1 second** of the navigation action for a week containing up to 100 session records, on the reference browser (§7.4).
- **Definition:** The remaining-time display updates at least once per second with no visible jank in the foreground tab.

### 4.4 Responsiveness and usability

- **Definition:** "Responsive" = the primary start action responds to input within **100 ms** in the foreground tab.
- **Definition:** The layout must remain usable at viewport widths down to **320 px** without horizontal scrolling of primary controls.

### 4.5 Accessibility

- **Baseline requirement:** The heat map must convey intensity by more than color alone (e.g., value labels or patterns), and interactive controls must be keyboard reachable. A formal accessibility audit and conformance target (e.g., WCAG level) are **out of scope** for this release and flagged as `[OPEN]` Q10 if a target is required for launch.

### 4.6 Privacy

- **Requirement:** No session data, settings, or usage telemetry is transmitted off the device in this release.

### 4.7 Cross-browser behavior

- **Requirement:** Supported browsers are not yet established (`[OPEN]` Q1). Until fixed, "supported" cannot be verified, and acceptance testing in §5.4 cannot be completed. This is a **blocking** dependency for release.

## 5. Acceptance Criteria

Each criterion states an observable, verifiable outcome. Categories: normal behavior, boundary cases, data consistency, and operating-environment limitations.

### 5.1 Normal feature behavior

- **AC-1:** From page load, activating the start-work control once displays a running countdown that begins at 25:00. *(FR-1)*
- **AC-2:** When a work interval reaches zero, a completed session record of type `work` with `plannedDurationSeconds = 1500` exists in storage. *(FR-1, FR-5)*
- **AC-3:** When a break interval reaches zero, a completed session record of type `break` with `plannedDurationSeconds = 300` exists in storage. *(FR-2, FR-5)*
- **AC-4:** Opening the heat map with no arguments displays the current week's seven day cells. *(FR-4)*
- **AC-5:** A day on which more completed work minutes were recorded renders at a strictly higher intensity than a day with fewer, and the legend is visible. *(FR-4)*
- **AC-6:** After completing a work interval and reloading the page, the session is still present in storage. *(FR-3, §4.2)*
- **AC-7:** `[PROPOSED]` Pausing a running interval freezes the displayed remaining time; resuming continues the countdown from the frozen value. *(FR-6)*

### 5.2 Boundary cases

- **AC-8:** A week containing no qualifying sessions renders seven zero-intensity cells, a visible legend, and no error message. *(FR-4, §3.3)*
- **AC-9:** Navigating from the current week to the previous week and back returns to the current week's grid with identical values. *(FR-4)*
- **AC-10:** A work session whose `startedAt` is on day D and `endedAt` is on day D+1 is counted entirely in day D's total. *(§3.3)*
- **AC-11:** `[PROPOSED]` Cancelling a running work interval produces no `completed` work session. *(FR-5, FR-6)*
- **AC-12:** `[PROPOSED]` Changing the work duration to a new value does not alter the remaining time of an interval already running; the next interval started uses the new value. *(FR-9)*
- **AC-13:** A week spanning a daylight-saving transition groups sessions into seven calendar-day buckets without merging or dropping a day. *(§3.3)*

### 5.3 Data consistency

- **AC-14:** For a set of N completed intervals, exactly N `completed` session records exist, each with a unique `id`. *(FR-5, §3.1)*
- **AC-15:** `[PROPOSED]` After deleting a session, the affected day's heat-map intensity decreases by that session's contribution, and no other day changes. *(FR-8, §3.3)*
- **AC-16:** Every session record contains all required fields of §3.1 with non-null values.
- **AC-17:** Session records written before a reload and after a reload share the same storage format version (`schemaVersion`), or are migrated without data loss. *(§3.2)*

### 5.4 Operating-environment limitations

- **AC-18:** With the tab backgrounded for longer than the remaining interval time, on returning to the tab the interval is finalized as completed and its recorded `endedAt` is within ±1 second of the true end time. *(§4.1)*
- **AC-19:** With system sleep occurring mid-interval and the machine waking after the end time, on wake the interval is finalized as completed and is counted in the heat map. *(§4.1)*
- **AC-20:** With notification permission denied, interval completion still produces the in-app visual signal and no error is shown to the user. *(FR-7, §7.2)*
- **AC-21:** With audio playback blocked by autoplay policy, interval completion still produces the in-app visual signal and the application does not fail. *(FR-7, §7.2)*
- **AC-22:** With the network disabled after initial page load, all of AC-1 through AC-19 still pass. *(O4)*
- **AC-23:** The heat map view renders within 1 second for a week of 100 session records on the reference browser. *(§4.3)*

### 5.5 Environment-dependent criteria that cannot yet be verified

- **AC-24:** The application passes AC-1 through AC-23 on each browser in the supported-browser list. **Cannot be verified until `[OPEN]` Q1 is resolved.**

## 6. Out of Scope

The following are explicitly excluded from this release. They are not committed and must not be implemented without a scope change.

- User accounts, authentication, and identity.
- Server-side storage, cloud sync, and cross-device synchronization.
- Any backend service or database. (Assumed unnecessary; see §7.1.)
- Task lists, task or project naming, tags, and associating sessions with work items.
- Long-break intervals (e.g., a longer break after four work intervals) and automatic multi-interval cycle scheduling.
- Historical analytics beyond the weekly heat map: monthly or yearly reports, trend lines, averages, streak counters, and goal setting.
- Data export or import in any format (CSV, JSON, iCal, etc.).
- Social, sharing, leaderboard, or team features.
- Integrations with calendars, issue trackers, or time-tracking services.
- Native mobile or desktop applications; this release is browser-only.
- Offline installability as a progressive web app, service worker caching, and push notifications. `[PROPOSED for a later release]`
- Theming, dark mode, and localization.
- Formal accessibility conformance auditing and certification.
- Monetization, licensing, and onboarding or account-creation flows.
- Notification while the application is fully closed (no service worker in this release).

## 7. Assumptions and Open Questions

### 7.1 Assumptions

| # | Assumption | If wrong |
|---|------------|----------|
| A1 | The application runs entirely client-side with no backend. | Persistence, notifications, and sync assumptions change materially; a backend becomes a dependency and O4 is affected. |
| A2 | Persistence uses browser storage (IndexedDB or equivalent) with `localStorage` acceptable for settings. | A server store is required and A1 is void. |
| A3 | Browser storage is retained across normal reloads and restarts but is **not durable**: it may be cleared by the user, by private-browsing session end, or by eviction under storage pressure. | If durable storage is required, a backend or export is required, which is currently out of scope. |
| A4 | A week is Monday–Sunday, fixed, not user-configurable. | Grouping logic and the heat map layout change. |
| A5 | The user grants notification permission; denial is handled by an in-app fallback. | None material — fallback already required. |
| A6 | The user's system clock is approximately correct and may change during a session. | Timer accuracy definition (§4.1) and session timestamps are affected; see Q9. |
| A7 | Default sound and notifications are enabled on first run. | First-run behavior and permission prompting change. |

### 7.2 Browser environment constraints and fallbacks

| Constraint | Effect on requested behavior | Fallback / decision |
|------------|------------------------------|---------------------|
| Background-tab timer throttling | Countdown callbacks are delayed or suppressed; a naive tick counter loses time | Compute from `startedAt` and wall-clock time (§4.1); reconcile on `visibilitychange`. **Decided — not optional.** |
| Page freeze / bfcache on suspend | Interval may "complete" while the page is not executing | Finalize on resume against true elapsed time (AC-19). **Decided.** |
| Notification API permission | System notification may be unavailable | In-app visual signal always present (AC-20). `[OPEN]` Q11: whether to prompt on first load or on first completion. |
| Autoplay policy for audio | Completion tone may be blocked until a user gesture occurs | In-app visual signal always present (AC-21). `[OPEN]` Q12: whether the first user interaction doubles as the audio unlock gesture. |
| Storage eviction / private browsing | Session history may be lost | Application must not claim durability (A3). `[OPEN]` Q13: whether to warn users in private browsing. |
| No service worker in scope | Notifications and timers do not run when the tab is closed | Interval abandoned when the page closes; FR-5 does not record it. `[OPEN]` Q14: whether the PWA/service-worker capability is promoted into this release. |

### 7.3 Product decisions vs. engineering implementation choices

**Product decisions** (product owns the answer; these change observable behavior):
- Q3 (below) — whether a break auto-starts after a work interval.
- Q6 — whether heat-map intensity encodes minutes or interval count.
- Q7 — whether midnight-spanning sessions are attributed whole or split.
- Q8 — whether intensity bands are fixed thresholds or relative to the week's maximum.
- Q4, Q5 — pause/cancel semantics and deletion reversibility.

**Engineering implementation choices** (engineering owns the answer; these do not change agreed behavior, provided the criteria in §5 hold):
- Whether persistence uses IndexedDB or `localStorage`, and the exact serialization format.
- How countdown rendering is scheduled (e.g., `requestAnimationFrame` vs. a 1-second interval), since accuracy is defined against wall-clock time, not callback count.
- How the heat-map intensity scale is implemented (color interpolation vs. discrete classes).
- How the week grid is laid out (rows vs. columns).

### 7.4 Implementation dependencies

- **Persistence format (D1)** depends on the session field set in §3.1 and the metric decision Q6. Q6 **blocks** the derived-data shape; the field set does not depend on Q6 and can proceed.
- **Timer accuracy mechanism (D2)** — wall-clock reconciliation — is a prerequisite for AC-18 and AC-19 and must be built with FR-1/FR-2, not retrofitted.
- **Notification and audio (D3)** depend on permission and autoplay behavior in the chosen browsers, which depend on Q1. Notification work can proceed against the fallback, but AC-20/AC-21 cannot be verified until Q1 is resolved.
- **Heat map (D4)** depends on D1 and on Q6, Q7, Q8.
- **Session list / deletion (D5, `[PROPOSED]`)** depends on D1 and Q5.
- **Supported-browser list (Q1)** is a **blocking** dependency for AC-24 and for the reference-browser threshold in §4.3.

## 8. Release Completion Conditions

The release is complete when **all** of the following are verifiable. Subjective statements such as "fully functional" or "product-ready" are not completion conditions.

1. **Functional correctness:** AC-1 through AC-6, and AC-7 if FR-6 is confirmed, pass on the reference browser.
2. **Boundary correctness:** AC-8 through AC-13 pass.
3. **Data consistency:** AC-14 through AC-17 pass, and a recorded session is present after a full browser restart, not only a reload.
4. **Environment behavior:** AC-18 through AC-22 pass, including the permission-denied and audio-blocked fallbacks.
5. **Performance:** AC-23 passes for a week of 100 records.
6. **Cross-browser:** AC-24 passes on every browser in the supported list defined by Q1.
7. **Decision closure:** Every `[OPEN]` question marked as blocking in §7.5 is resolved and its resolution is reflected in this document, or the affected requirement is removed from scope.
8. **Scope integrity:** No item in §6 (Out of Scope) is present in the shipped build.
